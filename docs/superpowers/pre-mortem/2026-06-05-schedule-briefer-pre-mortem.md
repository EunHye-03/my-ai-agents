# Pre-Mortem: schedule-briefer
_"3개월 후, schedule-briefer는 조용히 폐기됐다. 여기 실제로 무슨 일이 있었는지."_

> **역할:** Saboteur, Burned Expert (서브에이전트), Customer Advocate (Gemini), Pessimist (서브에이전트) — 4개 역할 종합.

---

## Executive Read

- **핵심 실패 스토리:** 7개 소스 중 하나라도 조용히 실패하면 브리핑 전체가 거짓말을 한다. EunHye는 이를 눈치채지 못하다가 마감을 놓친 뒤에야 도구를 포기한다.
- **가장 큰 제품 리스크:** 소스 실패 격리 없음 — 한 소스 오류가 전체 브리핑을 침묵시키거나 오염시킨다.
- **가장 큰 신뢰 리스크:** KNU 웹사이트 404 무음 처리 — 학교 공지를 놓쳐도 브리핑은 "공지 없음"으로 정상 출력된다.
- **가장 큰 감정적 상처 리스크:** Notion 할 일 무음 실패 — 도구의 결함이 사용자의 결함처럼 느껴진다 ("내가 Notion을 안 썼나?").
- **가장 큰 유지보수 리스크:** 7개 통합의 유지 비용이 "그냥 직접 확인하는 것"의 비용을 초과하는 순간 도구 사망.

## Moments of Truth Most Likely to Break

- **첫 자동 실행** → icalBuddy PATH 실패 → 일정 섹션 빈 채로 Slack 전송 → "일정이 없는 날"로 오해
- **KNU 사이트 리뉴얼** → 404 무음 처리 → 2주간 공지 누락 → 수강신청/장학금 놓침 → 즉각적 폐기 결정
- **Notion 할 일 빈 배열 반환** → "오늘 할 일 없음" 정상 출력 → 반복 → 마감 누락 → 자기 의심
- **Gmail 토큰 만료** → 전체 브리핑 중단 → Slack DM 미도착 → "오늘 조용한 날" 오해

## 🔴 Critical Risks (구현 전 반드시 해결)

### 1. 소스 실패 격리 없음 — 하나가 터지면 전체가 죽는다
**무엇이 잘못되는가:** Gmail MCP 토큰 만료처럼 하나의 소스가 예외를 던지면 에이전트 전체 실행이 중단된다.  
**사용자 경험:** Slack DM이 오지 않는다. EunHye는 "오늘 브리핑 없는 날"로 이해한다. 나머지 6개 소스의 정보를 전혀 받지 못한다.  
**감정적 영향:** 짜증 → 무력함. 뭘 고쳐야 하는지 알 수 없다.  
**빌더의 맹점:** 개별 소스는 각각 테스트했지만, 복합 실패 시나리오를 한 번도 테스트하지 않았다.  
**가능성:** High | **영향:** Catastrophic | **신뢰 손상:** High | **복구:** Moderate  
**자신감:** High  
**검증 방법:** Gmail MCP 토큰을 의도적으로 만료시킨 상태에서 브리핑 실행. 나머지 섹션이 정상 출력되는지 확인.  
**완화:** 각 소스를 try/catch로 격리. 실패 시 해당 섹션에 `⚠️ [소스명] 데이터 수집 실패` 명시.  
**트립와이어:** 브리핑에 섹션 하나라도 빠지거나 에러 메시지가 포함될 때.

---

### 2. icalBuddy PATH — 자동 실행 시 캘린더 섹션이 항상 비어 있다
**무엇이 잘못되는가:** `/schedule` 자동 실행은 non-interactive shell을 사용해 `~/.zshrc`의 PATH가 로드되지 않아 `icalBuddy`를 찾지 못한다.  
**사용자 경험:** 자동 브리핑은 일정 섹션이 항상 비어 있고, 수동 "브리핑해줘"는 정상 작동한다. 이 불일치를 한 달이 지나도 인지하지 못할 수 있다.  
**감정적 영향:** 혼란 — 같은 도구가 왜 어떨 때는 되고 어떨 때는 안 되는지 이해 불가.  
**빌더의 맹점:** 개발 중 터미널에서만 테스트. 자동 실행 환경은 한 번도 검증하지 않았다.  
**가능성:** High | **영향:** Catastrophic | **신뢰 손상:** High | **복구:** Easy (발견만 하면)  
**자신감:** High  
**검증 방법:** `/schedule` 실행 환경에서 `which icalBuddy` 확인. 또는 Bash 내에서 절대 경로 `/opt/homebrew/bin/icalBuddy` 강제 사용.  
**완화:** 에이전트 내 `icalBuddy` 호출 시 절대 경로 사용. 또는 PATH를 명시적으로 설정.  
**트립와이어:** 자동 브리핑과 수동 브리핑의 일정 섹션 결과가 다를 때.

---

### 3. KNU WebFetch 404 무음 처리 — 오류페이지 HTML을 정상 파싱
**무엇이 잘못되는가:** 학교 사이트 리뉴얼/서버 점검 시 WebFetch가 404 또는 로그인 리다이렉트 HTML을 받아와도 에이전트는 이를 "공지 없음"으로 처리한다.  
**사용자 경험:** 2주간 "학교 공지 없음" 출력. 수강신청, 장학금 공고 놓침. 동기한테 듣고 나서야 발견.  
**감정적 영향:** 분노 → 즉각적 도구 폐기. 신뢰 침식이 아닌 신뢰 폭발.  
**빌더의 맹점:** 배포 시 한 번 정상 동작 확인 후 재검증 없음. 대학 웹사이트는 예고 없이 URL 구조가 바뀐다.  
**가능성:** High | **영향:** Catastrophic | **신뢰 손상:** High | **복구:** Hard (신뢰는 기술로 복구 불가)  
**자신감:** High  
**검증 방법:** `curl -L -o /dev/null -w "%{http_code}" <URL>` 으로 3개 URL 상태 코드 매일 확인.  
**완화:** WebFetch 응답에 HTTP 상태 코드 검증 추가. 비정상 응답 시 `⚠️ KNU 사이트 접근 불가 (HTTP XXX)` 명시.  
**트립와이어:** 3개 소스 모두 동일 날 공지 없음이 연속 3일 이상 반복.

### 4. Notion MCP 무음 실패 — "할 일 없음"과 "조회 실패"가 동일하게 보인다
**무엇이 잘못되는가:** Notion API 토큰 만료, 페이지 구조 변경, 또는 API 버전 업데이트 시 MCP가 에러 없이 빈 배열을 반환한다.  
**사용자 경험:** 매일 "✅ 오늘 할 일: 없음" 출력. 마감 임박한 과제 3개가 쌓인 뒤 발견. "내가 Notion을 잘못 쓴 건가?" 자기 의심.  
**감정적 영향:** 배신감이 아닌 자기 의심 — 도구의 결함이 본인의 결함처럼 느껴진다. 가장 독한 신뢰 침식 패턴.  
**빌더의 맹점:** "MCP가 오류를 내면 알 것"이라는 가정. HTTP 200으로 빈 배열 반환은 성공으로 처리된다.  
**가능성:** High | **영향:** Catastrophic | **신뢰 손상:** High | **복구:** Hard  
**자신감:** High  
**검증 방법:** Notion MCP 직접 호출해 응답 구조 확인. 빈 배열 반환 시 에러 throw 여부 테스트.  
**완화:** Notion 응답이 빈 배열일 때 `⚠️ Notion 할 일 조회 결과 0건 (응답 확인 권장)` 경고 추가.  
**트립와이어:** 할 일 섹션이 3일 연속 0건.

---

### 5. Slack 전송 실패 무음 처리 — 빈 DM 전송 또는 배달 실패를 모른다
**무엇이 잘못되는가:** Slack MCP가 rate limit 또는 OAuth 토큰 만료(90일 주기)로 실패해도 에이전트는 전송 성공/실패를 검증하지 않는다.  
**사용자 경험:** Slack DM이 빈 채로 오거나 아예 오지 않는다. "오늘 조용한 날"로 오해. 수동 실행은 정상이어서 원인 파악이 더 어렵다.  
**감정적 영향:** 가스라이팅 — 본인의 기억과 현실 사이 불일치를 스스로 의심하게 된다.  
**빌더의 맹점:** 자동 실행 환경의 MCP 인증 상태가 인터랙티브 세션과 다를 수 있음을 고려하지 않았다.  
**가능성:** High | **영향:** Major | **신뢰 손상:** High | **복구:** Hard (언제부터 실패했는지 로그 없음)  
**자신감:** High  
**검증 방법:** `slack_send_message` 반환값 구조 확인. `ok: false` 케이스에서 에이전트 반응 테스트.  
**완화:** Slack 전송 후 응답 검증. 실패 시 로컬 파일에 기록 + 다음 수동 실행 시 경고 출력.  
**트립와이어:** Slack DM 히스토리에서 마지막 성공 전송이 24시간 이상 전일 때.

---

### 6. `/schedule` 자동 실행 — Claude Code 세션이 없으면 브리핑이 조용히 스킵된다
**무엇이 잘못되는가:** `/schedule` 자동 실행은 Claude Code 세션이 활성 상태여야 동작하는데, 노트북이 잠자기 상태이거나 Claude Code가 꺼져있으면 실행 자체가 스킵된다.  
**사용자 경험:** 밤에 노트북을 닫고 잔다. 오전 8시 예약 시간이 지나도 Slack DM 없음. 처음엔 노트북을 미리 켜두려 하지만 지속되지 않는다. 결국 자동 실행을 포기하고 수동 호출로만 쓰게 된다.  
**감정적 영향:** 체념 — "자동화가 되긴 하는데 내가 관리해줘야 하네."  
**빌더의 맹점:** `/schedule` 동작 방식을 정확히 파악하지 않고 "되겠지"라고 가정. 실제 실행 환경(macOS sleep, 세션 상태)을 테스트하지 않았다.  
**가능성:** High | **영향:** Catastrophic (자동 브리핑 핵심 기능 자체가 무력화) | **신뢰 손상:** High | **복구:** Hard  
**자신감:** High  
**검증 방법:** 노트북을 닫고 예약 시간이 지난 뒤 Slack DM이 왔는지 확인. `/schedule` 문서에서 세션 없이도 실행되는지 명시적으로 검증.  
**완화:** `/schedule` 대신 macOS `launchd` daemon으로 시스템 레벨 스케줄링 사용. 또는 자동 실행 기대치를 수동 호출로 낮추고 아침 루틴에 편입.  
**트립와이어:** 예약 시간 이후 30분 내 Slack DM이 오지 않을 때.  
**출처:** Pessimist (단독 발견)

## 🟠 Significant Risks (완화 계획 필요)

### 6. Gmail "중요" 필터 불투명 — 섹션 신뢰가 조용히 소멸된다
**무엇이 잘못되는가:** Gmail의 ML 기반 "중요" 분류가 사용자의 실제 우선순위와 일치하지 않는다.  
**사용자 경험:** 홍보 메일이 "중요"로 뜨고, 교수 메일이 누락된다. 직접 Gmail을 열면 미읽음 37개. 이후 이메일 섹션을 영구적으로 무시한다.  
**감정적 영향:** 냉소 — 조용히 섹션 하나가 죽는다.  
**가능성:** High | **영향:** Major | **신뢰 손상:** Partial  
**자신감:** High  
**검증 방법:** 브리핑 이메일 건수를 실제 Gmail 미읽음 건수와 당일 비교.  
**완화:** Gmail 쿼리를 `is:unread newer_than:1d`로 명시적 제한. "중요" 레이블 의존 제거.

### 7. git 스캔 성능 저하 — 레포 증가로 브리핑이 타임아웃된다
**무엇이 잘못되는가:** 레포 수 증가(현재 14개 → 6개월 후 20+개)로 `git log` 순차 실행 비용이 누적, 전체 브리핑 타임아웃.  
**사용자 경험:** 아침마다 브리핑이 느려지다가 어느 날 잘린 채로 전송.  
**감정적 영향:** 지침 → 수리 의욕 소멸.  
**가능성:** Medium | **영향:** Major  
**자신감:** Medium  
**완화:** 레포 목록 화이트리스트 또는 최대 스캔 수 상한(예: 10개) 설정.

### 8. MEMORY.md glob 범위 확장 — 오래된 컨텍스트가 브리핑을 오염시킨다
**무엇이 잘못되는가:** 프로젝트 증가에 따라 glob이 관련 없는 메모리 파일까지 수집, AI 컨텍스트 섹션이 비대해진다.  
**사용자 경험:** 3개월 전에 끝난 프로젝트 메모가 브리핑에 등장. 섹션이 길어져 스크롤 필요 → 섹션 무시.  
**감정적 영향:** 피로감.  
**가능성:** Medium | **영향:** Minor  
**자신감:** Medium  
**완화:** `ls -lt` 기준 최근 수정된 3개 파일만 읽도록 제한.

### 9. Claude Code 업데이트 후 MCP 버전 부정합 — 에이전트가 조용히 다른 결과를 반환한다
**무엇이 잘못되는가:** Claude Code 업데이트 후 MCP 프로토콜/파라미터 변경으로 Notion/Gmail/Slack 호출이 빈 응답을 반환한다.  
**사용자 경험:** 업데이트 후 Notion 할 일 섹션이 계속 비어있다. "내가 Notion을 잘 정리했나보다"라고 생각하다 마감 놓침.  
**감정적 영향:** 가스라이팅.  
**가능성:** Medium | **영향:** Major  
**자신감:** High  
**완화:** Claude Code 업데이트 후 각 MCP 소스를 수동으로 한 번씩 호출해서 결과 검증하는 체크리스트 유지.

## Cross-Cutting Themes

- **실패가 만들어낸 감정:** 자기 의심 ("내가 Notion을 잘못 쓴 건가?"), 가스라이팅 (브리핑은 정상인데 현실은 다름), 무력함 (고치고 싶은데 어디서 터진 건지 모름).
- **관계가 끊어진 순간:** 동기한테 "수강신청 어제였잖아"를 들은 그 순간. 도구를 믿었기 때문에 직접 확인하지 않았고, 도구가 거짓말을 했다.
- **이후 EunHye가 하는 말:** "AI 에이전트는 아직 못 믿겠어."

## The Uncomfortable Truth

7개 소스 통합의 복잡성이 문제가 아니다. **"없음"과 "실패"를 구분하지 않는 구조** 하나가 모든 것을 망친다. 에이전트가 완벽하게 작동해도, 각 소스가 빈 응답과 실패 응답을 동일하게 반환하는 한 이 도구는 항상 "정상처럼 보이는 거짓말쟁이"다.

그리고 더 불편한 진실 (Gemini, Customer Advocate): **EunHye는 도구 탓을 하지 않고 자기 탓을 한다.** "내가 설정을 잘못했나", "내가 API를 잘 모르나"라고 생각하며 조용히 포기한다. 도구가 만들어내는 자기 의심이 가장 독하다. 개인 자동화 도구가 죽는 진짜 이유는 기술적 오류가 아니라, **유지 비용이 "그냥 직접 확인하는 것"의 비용을 초과하는 순간**이다.
